# Microservice Scenario: DevOps Process Enrichment Overview

> English summary of [microservice-scenario-devops-process-enrichment-overview.md](microservice-scenario-devops-process-enrichment-overview.md).

## Background

Building on UModel, DevOps process enrichment adds development, release, artifact, and image entities to achieve end-to-end data modeling from code to container deployment, integrated with existing APM and K8s observability.

The scenario's `devops_data_generator` orchestrates 15 tasks that produce 7 entities: 6 in the DevOps domain (`user`, `repository`, `release`, `pull_request`, `artifact`, `docker_image`) plus `kubernetes_pod` in the K8s domain. Output entities and relationships are written to Alibaba Cloud SLS (Simple Log Service) LogStores; the k8s.pod topology is sourced from a CMS (Cloud Monitor Service) workspace EntityStore (or a local kubeconfig). The full UModel schema (17 EntitySet + 36 EntitySetLink) is generated by `tools/gen_umodel_yaml.py` into `umodel/`; the producer subset is documented in `config/data_mapping.yaml`.

## Core Value

### 1. End-to-End Traceability
- Code change → `release` → `artifact` → `docker_image` → K8s Pod → APM service
- Every step linked by UModel EntitySetLink relationships

### 2. Cross-Domain Data Integration
- Connect development data (`repository`, `release`, `pull_request`, `user`) with operations data (APM services, K8s pods)
- Enable root cause analysis that spans code changes and runtime behavior

### 3. Responsibility Attribution
- Map `user` to `repository`, services, and images
- Establish ownership chains for incident response

## Entity Relationship Overview

Relationship names follow the tasks registered in `devops_data_generator/tasks/` (15 tasks total). The `data_source` field is the identity/discriminator on every entity (not `git_provider`): GitLab records use `gitlab`, Codeup records use `codeup` (not `aliyun`), and ACR records use `aliyun_acr`.

```
DevOps domain (internal):
user            ──owns──►             repository          (user_owns_repository)
repository      ──tags──►             release              (repository_tags_release, direction repo→release, reversed from the old sourced_from)
repository      ──contains──►          pull_request        (repository_contains_pull_request)
user            ──participates_in──►  pull_request         (user_participates_in_pull_request, derived from authors + reviewers)
release         ──contains──►          artifact            (release_contains_artifact)
artifact        ──same_as──►          docker_image         (artifact_same_as_docker_image, ACR single-pass, decision B)

Cross-domain:
k8s.pod  ──uses──►  docker_image        (pod_uses_docker_image)
apm.service  ──sourced_from──►  repository      (static_topo)
apm.service  ──sourced_from──►  release         (static_topo)
user         ──manages──►        apm.service   (static_topo, renamed from developer_manages)
```

Entity renames (old → new): `developer` → `user`; `code_repository` → `repository`; `code_release` → `release`; `image` → `docker_image`. The `image_registry` entity was removed (decision A) — its registry-level attributes folded into `docker_image.registry`.

## Supported Git Providers

Code is fetched through the unified `IGitAdapter` interface (`devops_data_generator/adapters/base.py`) with two implementations: GitLab (`adapters/gitlab/adapter.py`) and Codeup (`adapters/codeup/adapter.py`). Each adapter's `get_provider_name()` returns the literal written into the `data_source` field of every record.

| Provider | SDK | Authentication |
|---|---|---|
| GitLab (self-hosted / SaaS) | python-gitlab 4.8.0 | Access Token (PAT / Project / Group) |
| Codeup (Alibaba Cloud) | alibabacloud-devops20210625 5.0.3 | RAM AK/SK or PAT |

Docker images and artifacts are produced by the ACR producer (`docker_image_task`, `data_source = "aliyun_acr"`), which fetches `docker_image` + `artifact` + the `artifact_same_as_docker_image` relation in a single pass (decision B).
